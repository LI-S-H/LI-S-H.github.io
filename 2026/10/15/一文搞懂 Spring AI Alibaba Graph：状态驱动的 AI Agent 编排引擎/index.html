2. 核心概念详解

2.1 心智模型：Graph 执行循环

三个关键推论：

  1. state 是唯一真相 — 节点之间不互相调用、不互相传参，只通过 state 通信
  2. 合并在判断之前 — 节点的返回值先合并进 state，dispatcher 才能看到
  3. 节点决定去哪，dispatcher 只负责传话

2.2 状态模型：OverAllState

为什么用 Map 而非对象？

不同节点写入不同字段，如果用对象风格，所有节点都要 import 整个 state 类，耦合会炸裂。Map 风格的"partial update"天然契合图的执行语义。

2.3 字段合并策略：KeyStrategyFactory

3. 节点与边

3.1 节点：NodeAction

3.2 边：普通边 vs 条件边

类型 代码 是否读 state 是否需要 Dispatcher
普通边 addEdge("a", "b") ❌ ❌
条件边 addConditionalEdges("a", dispatcher, Map) ✅ ✅

选择原则：

  • 目标唯一、无分支 → addEdge（性能更好）
  • 有分支（哪怕只有"继续/结束"） → addConditionalEdges

4. Dispatcher：拓扑与数据的翻译器

4.1 Dispatcher 的真实角色

Dispatcher 是个没有脑子的转发器。它不读业务数据、不做判断、不调 LLM，只做一件事：把节点刚才写进 state 的那个字符串，原样交给引擎。

4.2 完整数据流图

4.3 为什么 key 要带节点名前缀？

两个节点同时跑，各自的路由值互不干扰。 如果框架约定统一 key（都叫 __next_node__），那节点 A 写进去、节点 B 又覆盖，路由就乱了。

4.4 为什么 LLM 判断写在节点里？

原因 说明
配置依赖 Dispatcher 由 new XxxDispatcher() 无参构造，拿不到 ChatClient
流式输出 节点里的 LLM 可以 .stream() 把 token 实时推给前端
职责分离 节点 = "做事 + 汇报"，dispatcher = "传话"

9. 常见坑与最佳实践

坑 说明 解决方案
节点返回未注册的 key 引擎抛 KeyNotFoundException 用常量数组批量注册 ALL_KEYS
节点名拼错 路由表查不到，运行时抛异常 用常量而非字面量
依赖 ThreadLocal 节点在线程池里跑，拿不到上下文 把 userId 显式放进 state
节点里用共享可变成员变量 并行节点会互相踩 节点应该是无状态的，数据只走 state
state 字段塞大对象 每个 checkpoint 都要序列化 大字段委托给单独服务存储
忘记 interruptBefore HITL 节点不会挂起 在 CompileConfig 里配置

10. 速查表

API 作用 备注
OverAllState Map 式全局状态 节点间唯一通信方式
KeyStrategyFactory 登记每个 key 的合并策略 穷尽注册，漏了会抛异常
ReplaceStrategy 覆盖旧值 三个项目只用这一种
NodeAction 同步节点接口 apply(state) → Map 你只用实现这个
node_async(nodeAction) 同步包异步 装配时用
EdgeAction 同步条件边 apply(state) → String 你只用实现这个
StateGraph.addNode 注册节点 返回 this，可链式
StateGraph.addEdge 普通边（无条件） addEdge(A, B)
addConditionalEdges 条件边 + 路由表白名单 Map<返回值, 目标节点>
CompiledGraph.compile 编译图 在这里配 interruptBefore
RunnableConfig.threadId 会话/checkpoint 索引 多轮对话的钥匙
MemorySaver 内存 checkpoint 开发调试用
fluxStream(input, config) 流式执行图 SSE 入口
getState(config) 取最近 checkpoint 恢复时用
state.withResume() 标记恢复模式 恢复时必调
